# 설계 결정 기록 (Decision Log)

결정 하나에 항목 하나. 새 결정은 맨 아래에 번호를 이어서 추가하고, 바뀐 결정은 지우지 않고 상태를 `대체됨(D-xxx)`으로 바꾼다.

형식:

```
## D-xxx 제목
- 상태: 제안 | 확정 | 대체됨(D-yyy) | 예약(번호만 잡아 둠)
- 날짜: YYYY-MM-DD
- 결정: 한두 문장
- 이유: 왜 이걸 골랐나
- 대안: 검토했지만 고르지 않은 것과 이유
- 영향: 이 결정 때문에 지켜야 할 것
```

## D-001 데스크톱 프레임워크는 Tauri 2
- 상태: 확정
- 날짜: 2026-10-15
- 결정: Tauri 2(Rust 백엔드 + 웹 프론트엔드)로 만든다.
- 이유: 디자인 자유도가 가장 높고, 한글 입력이 OS 입력기를 그대로 써서 안정적이며, 앱 크기가 작다(5~15MB). Windows와 Ubuntu 모두 지원한다.
- 대안: egui(기본 모양이 개발 도구 느낌, 한글 IME 검증 필요), iced(0.14에서야 IME 지원, 1.0 전이라 API 변동), Slint(가능하나 웹보다 디자인 생태계가 작음), Electron(100MB 이상, 무거움).
- 영향: Ubuntu는 WebKitGTK, Windows는 WebView2로 그려지므로 두 OS에서 화면을 매번 확인한다. 브라우저 최신 기능(CSS 등)은 WebKitGTK 지원 여부를 확인하고 쓴다.

## D-002 지원 OS는 Windows 10/11과 Ubuntu 22.04 이상
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 1차 지원 대상은 Windows와 Ubuntu. macOS는 막지 않되 검증 대상은 아니다.
- 이유: 사용자가 두 OS 모두에서 쓴다.
- 영향: 경로 처리, 줄바꿈(CRLF/LF), 실행 파일 위치, 폴더 우클릭 메뉴는 OS별 구현이 필요하다. OS별 코드는 `platform` 모듈 한곳에 모은다.

## D-003 Git 처리는 설치된 git 명령 호출을 기본으로, 인터페이스 뒤에 숨긴다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 모든 Git 작업은 `GitBackend` 트레이트를 통해서만 한다. 첫 구현은 시스템 `git` CLI 호출(`CliBackend`)이다.
- 이유: 사용자의 기존 설정(자격 증명, hooks, .gitconfig, LFS)과 100% 같은 동작을 보장한다. 결과 파싱은 `--porcelain`, `-z` 등 기계용 출력만 쓴다.
- 대안: git2(libgit2, 일부 기능 미지원·자격 증명 처리 복잡), gitoxide(빠르지만 쓰기 기능이 아직 부분적).
- 영향: 읽기 성능이 중요한 곳(대형 저장소 log, status)은 나중에 gitoxide 구현으로 바꿀 수 있게 트레이트를 작게 유지한다. git 2.30 이상이 필요하며 앱 시작 시 확인한다.

## D-004 프론트엔드는 React + TypeScript + Vite
- 상태: 확정
- 날짜: 2026-10-15
- 결정: React 18 + TypeScript(strict) + Vite. 서버 상태는 TanStack Query, 화면 상태는 Zustand. 스타일은 CSS 변수(디자인 토큰) + CSS Modules.
- 이유: 생태계와 예제가 가장 많아 Claude Code와 함께 개발하기 쉽다. UI 라이브러리를 통째로 쓰지 않아 "흔한 템플릿 느낌"을 피한다.
- 대안: Svelte(가볍지만 생태계가 작음), Tailwind(빠르지만 토큰 일관성 관리가 흩어짐).
- 영향: 접근성이 필요한 기본 부품(메뉴, 대화상자, 툴팁)은 Radix UI Primitives(스타일 없는 부품)만 가져다 쓴다.

## D-005 모든 Git 기능은 "액션(Action)"으로 등록한다
- 상태: 대체됨(D-010)
- 날짜: 2026-10-15
- 결정: 기능 하나 = 액션 하나. 액션은 id, 쉬운 이름, 원래 Git 이름, 설명, 위험도, 미리보기, 실행, 되돌리기 방법을 갖고 레지스트리에 등록된다.
- 이유: 기능을 계속 추가해도 화면(버튼, 메뉴, 단축키, 명령 팔레트, 툴팁)이 레지스트리에서 자동으로 만들어진다. 확장성의 핵심.
- 영향: 화면 코드가 git 명령을 직접 부르지 않는다. 새 기능은 `docs/architecture.md`의 "새 액션 추가 절차"를 따른다.

## D-006 쉬운 이름 + 호버 시 원래 Git 이름 표시
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 화면에는 쉬운 이름("저장하기")을 쓰고, 마우스를 올리면 원래 이름과 명령("commit · git commit")과 한 줄 설명을 보여준다.
- 이유: 비전공자는 쉽게 쓰고, 익숙해지면 원래 Git 용어도 자연스럽게 배운다.
- 영향: 용어는 `glossary` 한 곳에서만 정의한다(`docs/spec.md`의 용어표가 원본). 화면에서는 반드시 `<Term id="commit">` 부품을 통해 표시한다. 설정에서 "Git 원래 이름으로 보기"로 전환할 수 있게 한다.

## D-007 위험한 작업은 미리보기 + 안전 백업 + 되돌리기
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 위험도가 `caution` 이상인 액션은 실행 전 미리보기를 보여주고, 실행 직전 현재 상태를 백업 참조(`refs/<app>/backup/<시각>`)로 남기고, 실행 후 "방금 작업 취소" 버튼을 띄운다.
- 이유: "잘못 커밋이나 기록 수정을 더 자유롭게"의 전제는 "망쳐도 돌아올 수 있다"는 안심이다.
- 영향: 백업 참조는 30일 뒤 자동 정리한다(설정 가능). 원격에 이미 올린 기록을 바꾸는 작업은 별도 경고 단계를 둔다.

## D-009 앱 이름은 `hiGit`
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 화면에 보이는 이름은 `hiGit`. 코드·패키지·실행 파일·경로에는 소문자 `higit`을 쓴다. `tauri.conf.json`의 `productName`은 `hiGit`, `identifier`는 `dev.higit.desktop`. 백업 참조는 `refs/higit/`, 작업 기록은 `.git/higit/`.
- 이유: 이름을 반복 0에서 정해 두면 출시 전에 identifier와 백업 참조 경로를 바꿀 일이 없다. identifier 끝을 `.app`으로 하지 않는 것은 Tauri가 macOS 번들 확장자와 겹친다고 경고하기 때문이다.
- 영향: 백업 참조 경로와 identifier는 사용자 데이터와 묶이므로 출시 후에는 바꾸지 않는다.

## D-010 상태를 바꾸는 기능은 Action, 조회는 Query로 나눈다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 상태를 바꾸는 Git 기능(저장하기, 합치기 등)은 `crates/core`의 `Action`으로 등록한다. 조회(status, log, diff, branches 등)는 Action에 넣지 않고 `crates/core`의 Query 경로(`core::query`)로 제공한다. 화면은 Action과 Query 모두 core를 통해서만 부르고 `GitBackend`를 직접 부르지 않는다. 용어 호버는 glossary id로 동작하므로 조회 화면도 `<Term>`을 그대로 쓴다.
- 이유: 조회는 미리보기·위험도·되돌리기가 필요 없다. 조회까지 Action으로 묶으면 실행기와 `Outcome`이 조회 결과 타입으로 부풀고, 레지스트리 메타(버튼·메뉴·명령 팔레트)에 버튼이 될 수 없는 항목이 섞인다.
- 대안: 조회도 Action(risk `Safe`)으로 등록하고 결과를 `Outcome` enum으로 돌려준다(규칙은 하나지만 실행기가 조회 타입을 알아야 함).
- 영향: D-005를 대체한다. "기능 하나 = Action 하나"는 상태를 바꾸는 기능에만 적용한다. Tauri 명령은 Action용 `action_*`와 조회용 `query_*`(예: `query_status`, `query_log`)로 나뉜다. 화면에 보내는 타입은 core의 view 타입이고 `crates/git` 타입을 그대로 노출하지 않는다(D-019).

## D-011 백업·되돌리기가 생기기 전까지 실행기는 caution 이상 액션을 거부한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 반복 0~1의 `Executor`는 미리보기 토큰 검사까지 구현하되, 백업 참조와 UndoJournal이 구현되는 반복 2 전까지 `Caution` 이상 액션 실행을 `NotYetSupported` 오류로 거부한다.
- 이유: D-007의 미리보기·백업·되돌리기 흐름을 우회하는 실행 경로를 처음부터 만들지 않는다.
- 대안: 반복 0에 백업 참조까지 구현(범위 확대), 경고만 띄우고 실행(D-007 위반).
- 영향: `discard` 등 `caution` 액션은 반복 2 이후에 등록한다.

## D-012 core 크레이트의 패키지 이름은 `higit-core`
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 폴더는 `src-tauri/crates/core`, 패키지 이름은 `higit-core`(코드에서 `higit_core`). 나머지 크레이트(`app`, `git`, `hosting`, `platform`, `watcher`)는 폴더 이름 그대로.
- 이유: 패키지 이름 `core`는 Rust 표준 `core` 크레이트를 가려 `::core::…`를 쓰는 매크로(serde 등)가 깨진다.
- 대안: 모든 크레이트에 `higit-` 접두사(일관되지만 `cargo run -p app` 등 기존 명령 표기가 바뀜).
- 영향: `cargo test -p higit-core`처럼 쓴다. 앱 이름(D-009)과 같은 접두사를 쓴다.

## D-013 개발 도구 버전과 줄바꿈
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 패키지 관리자는 pnpm(`package.json`의 `packageManager`로 버전 고정), Node는 22 LTS(`.nvmrc`와 `package.json`의 `engines`), Rust는 `rust-toolchain.toml`로 stable 특정 버전 고정. 저장소 텍스트 파일은 `.gitattributes`의 `* text=auto eol=lf`로 LF 고정(글꼴·이미지는 `binary`).
- 이유: Windows와 Ubuntu에서 같은 결과(잠금 파일, 포맷, 테스트)를 얻는다. Windows의 `core.autocrlf` 기본값으로 생기는 차이를 막는다.
- 대안: npm(기본 제공이지만 CLAUDE.md 명령이 pnpm 기준), 버전 미고정(환경마다 결과가 달라짐).
- 영향: 도구 버전을 올릴 때는 이 항목을 고치고 CI와 함께 올린다.

## D-014 글꼴은 Pretendard와 JetBrains Mono를 npm 패키지로 번들한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 본문은 Pretendard(한글·영문), 코드·해시·경로는 JetBrains Mono. 둘 다 SIL OFL 1.1이다. npm 패키지 `pretendard`, `@fontsource/jetbrains-mono`로 설치해 Vite가 앱에 번들하게 하고, 앱 크기를 줄이려고 Pretendard는 가변 글꼴 woff2 파일 하나(`PretendardVariable.woff2`)만, JetBrains Mono는 latin 부분의 400 굵기만 import한다. 각 글꼴의 OFL 원문은 `THIRD_PARTY_NOTICES.md`에 함께 둔다.
- 이유: OFL은 앱에 넣어 배포하는 것과 상업적 사용을 허용한다. 조건은 저작권 표시와 라이선스 원문을 함께 배포하는 것뿐이다. npm 패키지로 넣으면 버전이 잠금 파일에 고정되고 글꼴 파일을 저장소에 직접 커밋하지 않아도 된다.
- 대안: 글꼴 파일을 저장소에 직접 커밋(업데이트가 수동), 시스템 글꼴만 사용(OS마다 모양이 달라짐).
- 영향: 코드 글꼴은 400 하나만 쓴다. 코드에서 강조가 필요하면 색이나 배경으로 한다. 글꼴을 고치거나 이름을 바꾼 버전을 배포하려면 OFL의 예약 글꼴 이름 조건을 다시 확인한다.

## D-015 영어 용어표 `en.ts`도 반복 0에 만든다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: `src/glossary/en.ts`를 `ko.ts`와 같은 id로 반복 0에 만든다. 용어의 원본은 계속 `docs/spec.md` 표(한국어)다. 영어 문구의 원본은 `en.ts`이고, 테스트로 `ko.ts`와 id 집합이 같은지 확인한다. 언어를 바꾸는 설정 화면은 이후 반복에서 만든다.

## D-017 저장 기록·되돌리기·기록 정리의 시각화 방식
- 상태: 제안
- 날짜: 2026-10-15
- 결정: 저장 기록 기본 화면은 지하철 노선도 + 지도식 확대·축소 + 선 굵기(변경량)로 그린다. 안전망·되돌리기 화면은 게임 세이브 카드, 기록 정리하기 화면은 카드 지도로 만든다.
- 이유: 비전공자가 설명 없이 읽을 수 있는 표현을 여러 분야에서 비교한 결과다(`docs/research/git-visualization.md` "추천 조합").
- 대안: 일반 Git 도구식 그래프(익숙한 사람에게만 읽힘), 열차 운행 다이어그램·줄거리 차트(기본 화면보다 보조 보기에 적합). 조사 문서의 "검토했지만 뺀 것" 참고.
- 영향: 그리기 계층(배치 계산과 그리기)을 분리해 SVG로 시작하고 나중에 Canvas로 바꿀 수 있게 한다(`docs/architecture.md` "저장 기록 그리기 계층"). 확정 전까지 반복 0의 저장 기록 화면은 단순 목록이다.

## D-018 src-tauri는 app 크레이트 겸 워크스페이스 루트로 둔다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: Tauri 기본 구조를 따른다. `src-tauri/`가 `app` 패키지이면서 워크스페이스 루트이고, `tauri.conf.json`, `capabilities/`, `icons/`, `build.rs`도 `src-tauri/`에 둔다. 나머지 크레이트(`core`, `git`, `hosting`, `platform`, `watcher`)만 `src-tauri/crates/` 아래에 둔다.
- 이유: Tauri CLI가 기대하는 위치 그대로라 `tauri dev`/`build` 설정을 따로 지정할 필요가 없다.
- 대안: 가상 워크스페이스 + `crates/app`(구조는 대칭이지만 CLI 설정 위치를 확인·우회해야 함).
- 영향: 앱 코드는 `src-tauri/src/`에 있다. 의존 방향 규칙(`app → core → …`)은 그대로다.

## D-019 타입 바인딩은 tauri-specta를 정확한 RC 버전으로 고정하고 한 파일에 모은다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: `specta`, `tauri-specta`, `specta-typescript`를 `=`로 정확한 RC 버전에 고정한다. 명령 등록과 TS 내보내기 코드는 `src-tauri/src/bindings.rs` 한 파일에 모은다. 화면에 보내는 타입은 `crates/core`의 view 모듈(`core::view`)에만 두고, 바인딩용 derive는 그 모듈에만 붙인다. `crates/git`은 specta에 의존하지 않는다.
- 이유: RC라 API가 바뀔 수 있다. 문제가 생기면 ts-rs로 바꿀 때 고칠 곳이 `bindings.rs`와 `core::view` 두 곳으로 한정된다. `git` 크레이트를 작게 유지한다(D-003).
- 대안: git 타입에 derive를 직접 붙인다(변환 코드가 없지만 바인딩 라이브러리 교체 시 고칠 곳이 흩어짐). 타입을 손으로 쓴다(architecture.md가 금지).
- 영향: git 결과 타입을 view 타입으로 옮기는 변환 코드가 core에 생긴다. 바인딩 라이브러리를 바꾸면 이 항목을 대체하는 결정을 새로 쓴다.
