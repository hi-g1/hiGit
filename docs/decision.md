# 설계 결정 기록 (Decision Log)

결정 하나에 항목 하나. 새 결정은 맨 아래에 번호를 이어서 추가하고, 바뀐 결정은 지우지 않고 상태를 `대체됨(D-xxx)`으로 바꾼다.

형식:

```
## D-xxx 제목
- 상태: 제안 | 확정 | 대체됨(D-yyy) | 예약(번호만 잡아 둠)
- 날짜: YYYY-MM-DD
- 결정: 한두 문장
- 이유: 왜 이걸 골랐나
- 대안: 검토했지만 고르지 않은 것과 이유
- 영향: 이 결정 때문에 지켜야 할 것
```

## D-001 데스크톱 프레임워크는 Tauri 2
- 상태: 확정
- 날짜: 2026-10-15
- 결정: Tauri 2(Rust 백엔드 + 웹 프론트엔드)로 만든다.
- 이유: 디자인 자유도가 가장 높고, 한글 입력이 OS 입력기를 그대로 써서 안정적이며, 앱 크기가 작다(5~15MB). Windows와 Ubuntu 모두 지원한다.
- 대안: egui(기본 모양이 개발 도구 느낌, 한글 IME 검증 필요), iced(0.14에서야 IME 지원, 1.0 전이라 API 변동), Slint(가능하나 웹보다 디자인 생태계가 작음), Electron(100MB 이상, 무거움).
- 영향: Ubuntu는 WebKitGTK, Windows는 WebView2로 그려지므로 두 OS에서 화면을 매번 확인한다. 브라우저 최신 기능(CSS 등)은 WebKitGTK 지원 여부를 확인하고 쓴다.

## D-002 지원 OS는 Windows 10/11과 Ubuntu 22.04 이상
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 1차 지원 대상은 Windows와 Ubuntu. macOS는 막지 않되 검증 대상은 아니다.
- 이유: 사용자가 두 OS 모두에서 쓴다.
- 영향: 경로 처리, 줄바꿈(CRLF/LF), 실행 파일 위치, 폴더 우클릭 메뉴는 OS별 구현이 필요하다. OS별 코드는 `platform` 모듈 한곳에 모은다.

## D-003 Git 처리는 설치된 git 명령 호출을 기본으로, 인터페이스 뒤에 숨긴다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 모든 Git 작업은 `GitBackend` 트레이트를 통해서만 한다. 첫 구현은 시스템 `git` CLI 호출(`CliBackend`)이다.
- 이유: 사용자의 기존 설정(자격 증명, hooks, .gitconfig, LFS)과 100% 같은 동작을 보장한다. 결과 파싱은 `--porcelain`, `-z` 등 기계용 출력만 쓴다.
- 대안: git2(libgit2, 일부 기능 미지원·자격 증명 처리 복잡), gitoxide(빠르지만 쓰기 기능이 아직 부분적).
- 영향: 읽기 성능이 중요한 곳(대형 저장소 log, status)은 나중에 gitoxide 구현으로 바꿀 수 있게 트레이트를 작게 유지한다. git 2.30 이상이 필요하며 앱 시작 시 확인한다.

## D-004 프론트엔드는 React + TypeScript + Vite
- 상태: 확정
- 날짜: 2026-10-15
- 결정: React 18 + TypeScript(strict) + Vite. 서버 상태는 TanStack Query, 화면 상태는 Zustand. 스타일은 CSS 변수(디자인 토큰) + CSS Modules.
- 이유: 생태계와 예제가 가장 많아 Claude Code와 함께 개발하기 쉽다. UI 라이브러리를 통째로 쓰지 않아 "흔한 템플릿 느낌"을 피한다.
- 대안: Svelte(가볍지만 생태계가 작음), Tailwind(빠르지만 토큰 일관성 관리가 흩어짐).
- 영향: 접근성이 필요한 기본 부품(메뉴, 대화상자, 툴팁)은 Radix UI Primitives(스타일 없는 부품)만 가져다 쓴다.

## D-005 모든 Git 기능은 "액션(Action)"으로 등록한다
- 상태: 대체됨(D-010)
- 날짜: 2026-10-15
- 결정: 기능 하나 = 액션 하나. 액션은 id, 쉬운 이름, 원래 Git 이름, 설명, 위험도, 미리보기, 실행, 되돌리기 방법을 갖고 레지스트리에 등록된다.
- 이유: 기능을 계속 추가해도 화면(버튼, 메뉴, 단축키, 명령 팔레트, 툴팁)이 레지스트리에서 자동으로 만들어진다. 확장성의 핵심.
- 영향: 화면 코드가 git 명령을 직접 부르지 않는다. 새 기능은 `docs/architecture.md`의 "새 액션 추가 절차"를 따른다.

## D-006 쉬운 이름 + 호버 시 원래 Git 이름 표시
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 화면에는 쉬운 이름("저장하기")을 쓰고, 마우스를 올리면 원래 이름과 명령("commit · git commit")과 한 줄 설명을 보여준다.
- 이유: 비전공자는 쉽게 쓰고, 익숙해지면 원래 Git 용어도 자연스럽게 배운다.
- 영향: 용어는 `glossary` 한 곳에서만 정의한다(`docs/spec.md`의 용어표가 원본). 화면에서는 반드시 `<Term id="commit">` 부품을 통해 표시한다. 설정에서 "Git 원래 이름으로 보기"로 전환할 수 있게 한다.

## D-007 위험한 작업은 미리보기 + 안전 백업 + 되돌리기
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 위험도가 `caution` 이상인 액션은 실행 전 미리보기를 보여주고, 실행 직전 현재 상태를 백업 참조(`refs/<app>/backup/<시각>`)로 남기고, 실행 후 "방금 작업 취소" 버튼을 띄운다.
- 이유: "잘못 커밋이나 기록 수정을 더 자유롭게"의 전제는 "망쳐도 돌아올 수 있다"는 안심이다.
- 영향: 백업 참조는 30일 뒤 자동 정리한다(설정 가능). 원격에 이미 올린 기록을 바꾸는 작업은 별도 경고 단계를 둔다.

## D-009 앱 이름은 `hiGit`
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 화면에 보이는 이름은 `hiGit`. 코드·패키지·실행 파일·경로에는 소문자 `higit`을 쓴다. `tauri.conf.json`의 `productName`은 `hiGit`, `identifier`는 `dev.higit.desktop`. 백업 참조는 `refs/higit/`, 작업 기록은 `.git/higit/`.
- 이유: 이름을 반복 0에서 정해 두면 출시 전에 identifier와 백업 참조 경로를 바꿀 일이 없다. identifier 끝을 `.app`으로 하지 않는 것은 Tauri가 macOS 번들 확장자와 겹친다고 경고하기 때문이다.
- 영향: 백업 참조 경로와 identifier는 사용자 데이터와 묶이므로 출시 후에는 바꾸지 않는다.

## D-010 상태를 바꾸는 기능은 Action, 조회는 Query로 나눈다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 상태를 바꾸는 Git 기능(저장하기, 합치기 등)은 `crates/core`의 `Action`으로 등록한다. 조회(status, log, diff, branches 등)는 Action에 넣지 않고 `crates/core`의 Query 경로(`core::query`)로 제공한다. 화면은 Action과 Query 모두 core를 통해서만 부르고 `GitBackend`를 직접 부르지 않는다. 용어 호버는 glossary id로 동작하므로 조회 화면도 `<Term>`을 그대로 쓴다.
- 이유: 조회는 미리보기·위험도·되돌리기가 필요 없다. 조회까지 Action으로 묶으면 실행기와 `Outcome`이 조회 결과 타입으로 부풀고, 레지스트리 메타(버튼·메뉴·명령 팔레트)에 버튼이 될 수 없는 항목이 섞인다.
- 대안: 조회도 Action(risk `Safe`)으로 등록하고 결과를 `Outcome` enum으로 돌려준다(규칙은 하나지만 실행기가 조회 타입을 알아야 함).
- 영향: D-005를 대체한다. "기능 하나 = Action 하나"는 상태를 바꾸는 기능에만 적용한다. Tauri 명령은 Action용 `action_*`와 조회용 `query_*`(예: `query_status`, `query_log`)로 나뉜다. 화면에 보내는 타입은 core의 view 타입이고 `crates/git` 타입을 그대로 노출하지 않는다(D-019).

## D-011 백업·되돌리기가 생기기 전까지 실행기는 caution 이상 액션을 거부한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 반복 0~1의 `Executor`는 미리보기 토큰 검사까지 구현하되, 백업 참조와 UndoJournal이 구현되는 반복 2 전까지 `Caution` 이상 액션 실행을 `NotYetSupported` 오류로 거부한다.
- 이유: D-007의 미리보기·백업·되돌리기 흐름을 우회하는 실행 경로를 처음부터 만들지 않는다.
- 대안: 반복 0에 백업 참조까지 구현(범위 확대), 경고만 띄우고 실행(D-007 위반).
- 영향: `discard` 등 `caution` 액션은 반복 2 이후에 등록한다.

## D-012 core 크레이트의 패키지 이름은 `higit-core`
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 폴더는 `src-tauri/crates/core`, 패키지 이름은 `higit-core`(코드에서 `higit_core`). 나머지 크레이트(`app`, `git`, `hosting`, `platform`, `watcher`)는 폴더 이름 그대로.
- 이유: 패키지 이름 `core`는 Rust 표준 `core` 크레이트를 가려 `::core::…`를 쓰는 매크로(serde 등)가 깨진다.
- 대안: 모든 크레이트에 `higit-` 접두사(일관되지만 `cargo run -p app` 등 기존 명령 표기가 바뀜).
- 영향: `cargo test -p higit-core`처럼 쓴다. 앱 이름(D-009)과 같은 접두사를 쓴다.

## D-013 개발 도구 버전과 줄바꿈
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 패키지 관리자는 pnpm(`package.json`의 `packageManager`로 버전 고정), Node는 22 LTS(`.nvmrc`와 `package.json`의 `engines`), Rust는 `rust-toolchain.toml`로 stable 특정 버전 고정. 저장소 텍스트 파일은 `.gitattributes`의 `* text=auto eol=lf`로 LF 고정(글꼴·이미지는 `binary`).
- 이유: Windows와 Ubuntu에서 같은 결과(잠금 파일, 포맷, 테스트)를 얻는다. Windows의 `core.autocrlf` 기본값으로 생기는 차이를 막는다.
- 대안: npm(기본 제공이지만 CLAUDE.md 명령이 pnpm 기준), 버전 미고정(환경마다 결과가 달라짐).
- 영향: 도구 버전을 올릴 때는 이 항목을 고치고 CI와 함께 올린다.

## D-014 글꼴은 Pretendard와 JetBrains Mono를 npm 패키지로 번들한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 본문은 Pretendard(한글·영문), 코드·해시·경로는 JetBrains Mono. 둘 다 SIL OFL 1.1이다. npm 패키지 `pretendard`, `@fontsource/jetbrains-mono`로 설치해 Vite가 앱에 번들하게 하고, 앱 크기를 줄이려고 Pretendard는 가변 글꼴 woff2 파일 하나(`PretendardVariable.woff2`)만, JetBrains Mono는 latin 부분의 400 굵기만 import한다. 각 글꼴의 OFL 원문은 `THIRD_PARTY_NOTICES.md`에 함께 둔다.
- 이유: OFL은 앱에 넣어 배포하는 것과 상업적 사용을 허용한다. 조건은 저작권 표시와 라이선스 원문을 함께 배포하는 것뿐이다. npm 패키지로 넣으면 버전이 잠금 파일에 고정되고 글꼴 파일을 저장소에 직접 커밋하지 않아도 된다.
- 대안: 글꼴 파일을 저장소에 직접 커밋(업데이트가 수동), 시스템 글꼴만 사용(OS마다 모양이 달라짐).
- 영향: 코드 글꼴은 400 하나만 쓴다. 코드에서 강조가 필요하면 색이나 배경으로 한다. 글꼴을 고치거나 이름을 바꾼 버전을 배포하려면 OFL의 예약 글꼴 이름 조건을 다시 확인한다.

## D-015 영어 용어표 `en.ts`도 반복 0에 만든다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: `src/glossary/en.ts`를 `ko.ts`와 같은 id로 반복 0에 만든다. 용어의 원본은 계속 `docs/spec.md` 표(한국어)다. 영어 문구의 원본은 `en.ts`이고, 테스트로 `ko.ts`와 id 집합이 같은지 확인한다. 언어를 바꾸는 설정 화면은 이후 반복에서 만든다.

## D-017 저장 기록·되돌리기·기록 정리의 시각화 방식
- 상태: 제안
- 날짜: 2026-10-15
- 결정: 저장 기록 기본 화면은 지하철 노선도 + 지도식 확대·축소 + 선 굵기(변경량)로 그린다. 안전망·되돌리기 화면은 게임 세이브 카드, 기록 정리하기 화면은 카드 지도로 만든다.
- 이유: 비전공자가 설명 없이 읽을 수 있는 표현을 여러 분야에서 비교한 결과다(`docs/research/git-visualization.md` "추천 조합").
- 대안: 일반 Git 도구식 그래프(익숙한 사람에게만 읽힘), 열차 운행 다이어그램·줄거리 차트(기본 화면보다 보조 보기에 적합). 조사 문서의 "검토했지만 뺀 것" 참고.
- 영향: 그리기 계층(배치 계산과 그리기)을 분리해 SVG로 시작하고 나중에 Canvas로 바꿀 수 있게 한다(`docs/architecture.md` "저장 기록 그리기 계층"). 확정 전까지 반복 0의 저장 기록 화면은 단순 목록이다.

## D-018 src-tauri는 app 크레이트 겸 워크스페이스 루트로 둔다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: Tauri 기본 구조를 따른다. `src-tauri/`가 `app` 패키지이면서 워크스페이스 루트이고, `tauri.conf.json`, `capabilities/`, `icons/`, `build.rs`도 `src-tauri/`에 둔다. 나머지 크레이트(`core`, `git`, `hosting`, `platform`, `watcher`)만 `src-tauri/crates/` 아래에 둔다.
- 이유: Tauri CLI가 기대하는 위치 그대로라 `tauri dev`/`build` 설정을 따로 지정할 필요가 없다.
- 대안: 가상 워크스페이스 + `crates/app`(구조는 대칭이지만 CLI 설정 위치를 확인·우회해야 함).
- 영향: 앱 코드는 `src-tauri/src/`에 있다. 의존 방향 규칙(`app → core → …`)은 그대로다.

## D-019 타입 바인딩은 tauri-specta를 정확한 RC 버전으로 고정하고 한 파일에 모은다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: `specta`, `tauri-specta`, `specta-typescript`를 `=`로 정확한 RC 버전에 고정한다. 명령 등록과 TS 내보내기 코드는 `src-tauri/src/bindings.rs` 한 파일에 모은다. 화면에 보내는 타입은 `crates/core`의 view 모듈(`core::view`)에만 두고, 바인딩용 derive는 그 모듈에만 붙인다. `crates/git`은 specta에 의존하지 않는다.
- 이유: RC라 API가 바뀔 수 있다. 문제가 생기면 ts-rs로 바꿀 때 고칠 곳이 `bindings.rs`와 `core::view` 두 곳으로 한정된다. `git` 크레이트를 작게 유지한다(D-003).
- 대안: git 타입에 derive를 직접 붙인다(변환 코드가 없지만 바인딩 라이브러리 교체 시 고칠 곳이 흩어짐). 타입을 손으로 쓴다(architecture.md가 금지).
- 영향: git 결과 타입을 view 타입으로 옮기는 변환 코드가 core에 생긴다. 바인딩 라이브러리를 바꾸면 이 항목을 대체하는 결정을 새로 쓴다.

## D-020 액션 입력은 액션별 구조체와 태그 붙은 `ActionInput` enum으로 받는다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 액션마다 입력 구조체(`CommitInput { message }` 등)를 두고, 화면은 `ActionInput` enum(`#[serde(tag = "id", content = "input", rename_all = "kebab-case")]`, 입력 없는 액션은 unit 변형)으로 보낸다. 타입은 `core::view`에 두고 바인딩 derive도 거기에만 붙인다(D-019). `Action` 트레이트는 `&serde_json::Value` 대신 `&ActionInput`을 받는다. `action_preview`·`action_execute`의 별도 `id` 인자는 없애고 enum 태그에서 id를 얻는다. `ActionMeta.input_schema`는 없앤다.
- 이유: `BTreeMap<String, String>`은 문자열만 담고 필드 이름 오타·빠진 필드를 컴파일러가 잡지 못한다. 태그 enum은 TS에서 판별 유니온이 되어 화면 코드도 타입 검사를 받는다. specta rc.25가 재귀 타입(`Value`)을 내보내지 못하는 문제도 사라진다. 입력이 있는 액션은 어차피 전용 UI(`src/features/<id>/`)가 필요해 범용 폼 스키마의 쓰임이 없다.
- 대안: `BTreeMap` 유지(타입 안전성 없음). 트레이트에 연관 타입 `type Input`(레지스트리를 동적으로 유지하려면 타입 지우기 래퍼가 필요해 복잡). `input_schema` 유지(구조체와 이중 정의가 생기고 맞는지 검사가 필요).
- 영향: 새 액션 추가 절차에 "`core::view`의 `ActionInput`에 변형 추가"가 들어간다. `architecture.md`의 Action 트레이트·`ActionMeta`·"프론트와 백엔드 계약" 절을 함께 고친다. 명령 팔레트가 생기면 입력 필요 여부를 그때 메타에 다시 정한다.

## D-021 git 실패 분류에 한해 영어 stderr 고정 문구를 읽는다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 성공 출력은 계속 기계용 형식만 파싱한다(D-003). 실패한 명령의 종류(인증 실패, 앞서 나감 거부, 덮어쓸 파일 있음, 이름 없음 등)를 가리는 데에 한해 `LC_ALL=C`로 받은 stderr의 고정 영어 문구를 `crates/git`의 분류 함수 한곳에서 읽는다. 알아보지 못한 실패는 일반 `GitFailed`로 두고 원문은 "자세히 보기"로 보여준다.
- 이유: git은 실패 이유를 기계용 형식으로 주지 않는다. 쉬운 안내와 해결 버튼(spec.md "오류 메시지 원칙")을 주려면 분류가 필요하다. 반복 0의 `discover`가 이미 같은 방식을 쓴다.
- 대안: 분류하지 않고 모두 `GitFailed`(안내가 쓸모없어짐). 명령 전에 상태를 미리 검사(경쟁 상태가 생기고 모든 경우를 막지 못함).
- 영향: 분류 문구는 `crates/git`의 한 파일에만 두고, 문구마다 실제 git으로 재현하는 테스트를 둔다. git 버전이 바뀌어 문구가 달라져도 `GitFailed`로 떨어질 뿐 동작은 깨지지 않는다. 사용자 환경이 한국어 로케일(`LANG=ko_KR.UTF-8`, `LANGUAGE=ko`)이어도 영어 원문이 나오는지 테스트로 고정한다(`LANGUAGE`는 비워서 실행). SSH 실패는 호스트 확인 실패와 키·인증 실패를 구분해 다른 안내를 준다.

## D-022 커밋 전 검사는 저장소에 포함한 git hook으로 강제한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: hook 파일을 `.githooks/`에 두고 `core.hooksPath=.githooks`로 쓴다. 설정은 `pnpm install`의 `prepare` 스크립트(`scripts/install-hooks.mjs`)가 한다. hook은 얇은 POSIX sh이고 실제 검사는 `scripts/check.mjs`(Node)가 한다. pre-commit은 스테이지된 파일 기준으로 바뀐 쪽만 빠르게 검사한다(`src/` 등 프론트: lint·typecheck·vitest, `src-tauri/`: fmt·clippy). pre-push는 전체 검사(프론트 전부, fmt, clippy, `cargo test --workspace`, 바인딩 최신)를 한다.
- 이유: Windows(Git for Windows의 sh)와 Ubuntu에서 같은 스크립트가 돌려면 sh는 Node 호출만 하고 명령 실행은 Node가 하는 편이 안전하다(`.cmd` 실행, 경로 구분자). `prepare`로 설치하면 clone 후 따로 할 일이 없다.
- 대안: husky·lefthook(의존성 추가), 수동 `git config`(빠뜨리기 쉬움), 모든 검사를 pre-commit에(Rust 테스트가 느려 커밋이 무거움).
- 영향: CLAUDE.md "명령"·"커밋" 절과 README에 hook과 `pnpm check:fast`/`check:full`을 적는다. `--no-verify`는 쓰지 않는다. 사용자의 개인 `.git/hooks`는 이 저장소에서 쓰이지 않는다. Rust 테스트는 push 때 확인되므로, Rust 코드를 고친 커밋은 커밋 전에 `pnpm check:full`을 돌리는 것을 원칙으로 한다(CLAUDE.md "테스트가 실패하는 상태로 커밋하지 않는다").

## D-023 네트워크 git 작업은 사용자가 정하지 않았을 때 SSH 질문을 끈다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: fetch·pull·push에 한해, 사용자가 `GIT_SSH_COMMAND` 환경 변수나 `core.sshCommand` 설정을 따로 두지 않았으면 `GIT_SSH_COMMAND="ssh -o BatchMode=yes"`를 준다. 질문(호스트 키 확인, 키 비밀번호) 대신 실패하고, 실패는 D-021 분류로 "처음 접속하는 서버라 확인이 필요해요"와 "SSH 키 비밀번호나 인증이 필요해요"를 나눠 안내한다. HTTPS 자격 증명 도우미(Windows Git Credential Manager 창 등)는 막지 않는다.
- 이유: 앱에는 SSH 질문에 답할 화면이 없다. 터미널에서 띄운 앱은 질문을 기다리며 멈추고, 데스크톱에서 띄운 앱은 이유 없이 실패한다.
- 대안: 건드리지 않음(D-003 "사용자 설정과 같은 동작"에 더 가깝지만 멈춤이 생긴다). 앱 안에 SSH 질문 대화상자(SSH_ASKPASS 구현, 범위가 큼).
- 영향: D-003을 네트워크 작업에서 좁게 보완한다. 사용자가 SSH 설정을 직접 둔 경우는 그대로 따른다. 키 비밀번호가 필요한 사용자는 ssh-agent에 키를 올려야 한다는 안내가 필요하다.

## D-024 화면 용어는 억지 번역 대신 이미 아는 말을 쓴다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 쉬운 이름을 정하는 기준을 `docs/research/terminology.md` "기준" 1~6으로 정하고, 그 문서의 "바꿀 안" 표를 채택한다(예: 작업 갈래 → 브랜치, 저장하기 → 버전 저장, 저장 기록 → 버전 기록, 바뀐 내용 → 변경 사항, 안전망 → 복구). 표에 없는 `unstage`·`switch`는 같은 기준으로 "이번 버전에서 빼기"·"브랜치 바꾸기"로 맞춘다. 표와 달리 cherry-pick은 "이 버전만 복사하기"("가져오기"는 pull에만), reset은 "이 버전으로 돌아가기"(revert "되돌리기"와 동사를 나눔)로 한다. tag는 "태그" 그대로 두고 설명을 "이 버전에 v1.0 같은 이름 붙이기"로 해, "버전"은 commit 한 뜻으로만 쓴다(구글 문서의 "버전 이름 지정"과 같은 감각). 호버 설명은 동작이면 "~하기", 대상이면 명사로 끝내고 "~않음·~함·~사라짐" 같은 메모체를 쓰지 않는다. 주의할 내용은 둘째 문장에 "~요"로 쓴다. 용어 id(코드 식별자)는 바꾸지 않고 쉬운 이름과 호버 설명만 바꾼다. 영어 `en.ts`도 같은 뜻으로 고친다.
- 이유: 지금 표는 hiGit에서만 통하는 은유("갈래 옮겨 심기", "새 소식 확인")가 많아 밖에서 Git을 배울 때 이어지지 않는다. "저장하기"는 파일 저장(Ctrl+S)과 헷갈린다. 구글 문서·VS Code 한국어판처럼 이미 익숙한 말을 쓰면 설명이 덜 필요하다.
- 대안: 지금 표 유지(은유를 한 번 더 풀어야 함). 원어 그대로(비전공자에게 낯섦). id까지 바꾸기(액션 태그·바인딩·테스트가 함께 바뀌는데 사용자에게 보이는 이득이 없음).
- 영향: D-006을 보완한다. 한국어로 굳은 외래어(브랜치, 태그, 리베이스)는 그 자체가 쉬운 이름이 될 수 있고, 호버에는 여전히 원래 이름·명령·설명이 뜬다. 바꿀 때는 `docs/spec.md` 용어표, `src/glossary/ko.ts`·`en.ts`, 화면 문구(`src/messages`)를 한 번에 고친다. 액션 이름표는 glossary에서 오므로 `action-meta.json`·`ActionInput`은 바뀌지 않는다. 계획: `docs/plans/002-terms-and-design-refresh.md`.

## D-025 작업 공간은 2단 + 상단 바로 배치한다
- 상태: 확정
- 날짜: 2026-10-15

## D-026 색은 먹색 모노, 주 버튼은 흑연색 `#4A5059`
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 틀은 무채색으로 하고 주 버튼은 흑연색 채움(라이트 `#4A5059` + 흰 글자, 다크 `#C9CBCE` + `#161718` 글자)으로 한다. 파랑(`--accent`)은 선택 표시·키보드 포커스·링크에만 쓴다. 그 밖의 색은 브랜치 선, 파일 상태(추가·수정·삭제), 위험 작업처럼 뜻이 있을 때만 쓴다. 본문 글자는 `#24292F`. 주 버튼 색은 새 토큰 `--primary`, `--primary-hover`, `--primary-text`로 두고, 바탕은 `--bg`·`--surface`·`--surface-sunken` 세 단계로 한다. 값과 대비는 `docs/plans/002-terms-and-design-refresh.md`의 표를 따르고, 모든 글자 대비가 WCAG AA(4.5:1, 테두리·포커스는 3:1) 이상인지 테스트로 확인한다. 조사 문서 값 중 AA에 못 미치는 보조 글자는 `#6A6F75`, 추가 표시는 `#2D7A4D`로 바꿔 쓴다. 현재 브랜치는 색이 아니라 표시와 굵기로 구분한다.

## D-027 화면 문구에 괄호 보충을 쓰지 않는다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 화면 문구에 괄호로 덧붙이는 설명을 쓰지 않는다. 버튼은 한 가지 동작을 동사로 끝나는 짧은 말로 쓴다(목적어는 붙여도 된다, 예: "폴더 열기"). 보충 설명은 `<Term>` 툴팁, 일반 툴팁, 또는 둘째 줄로 보여준다.
- 이유: "합치기 그만두기 (원래대로)" 같은 괄호 보충은 자동 생성 문구의 대표 습관이고, 버튼이 길어져 무엇을 누르는지 흐려진다.
- 대안: 괄호 허용(짧게 보충할 수 있지만 문구 품질이 들쭉날쭉해짐).
- 영향: `docs/design.md`에 문구 규칙으로 넣고, `src/messages`·`src/glossary`에 괄호가 없는지 테스트로 확인한다.

## D-029 문장 속 Git 용어는 호버 없이 쉬운 이름만, glossary에서 꺼내 쓴다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 오류 안내·빈 상태 같은 문장 안에 들어가는 Git 용어는 `<Term>`(호버)을 붙이지 않고 쉬운 이름만 쓴다. 단, 글자를 문구 파일에 직접 쓰지 않고 `src/glossary`의 쉬운 이름을 꺼내 끼운다(`src/messages/ko.ts`·`en.ts`의 `t(id)`). 받침에 따라 달라지는 조사는 `src/messages/josa.ts`로 고른다. 버튼·제목·탭 같은 화면 요소의 용어는 지금처럼 `<Term>`을 쓴다.

- 영향: D-006을 보완한다. 문장 속 용어는 "Git 원래 이름으로 보기" 설정을 따르지 않고 늘 쉬운 이름이다. `src/messages/terms-in-messages.test.ts`가 용어표를 바꾸면 문장이 함께 바뀌는지 확인한다.

## D-031 시작 화면은 "마지막으로 하던 곳"을 크게 보여주는 배치로 한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 시작 화면은 위에서 아래로 상단 바, "마지막으로 하던 곳", "다른 프로젝트" 세 부분이다(`docs/research/start-screen.md`). "마지막으로 하던 곳"은 `--bg` 바탕에 작은 글자 "마지막으로 하던 곳 · 10분 전", 프로젝트 이름(26px)과 경로, 상태 문장, 그 프로젝트의 노선도, 주 버튼 "이어서 하기"와 글자 버튼 "바뀐 파일 N개 보기"를 둔다. "다른 프로젝트"는 `--surface` 바탕의 목록이고 줄마다 이름, 작은 노선도, 짧은 상태, 마지막으로 연 때를 둔다. 처음 실행이면 "마지막으로 하던 곳" 자리에 이름·이메일 설정을 둔다(마법사 화면을 따로 두지 않는다). 색은 큰 노선도의 선과 점만 브랜치 색(`--graph-*`), 작은 노선도는 `--border-strong`이고 갈라진 브랜치만 `--text-muted`, 상태 글자는 본문색이고 충돌만 `--deleted`. 노선도 옆 글자("지금 여기", 브랜치 이름, 버전 이름)는 브랜치 색이 아니라 `--text`·`--text-muted`로 쓴다. 흐린 줄(사라진 폴더)은 투명도 대신 `--text-muted` 글자로 만든다. 상태 문장과 노선도는 화면이 먼저 이름과 시간만 그리고 core Query로 나중에 채운다. 노선도 그리기는 버전 기록 화면과 같은 층(데이터 → 화면 모델 → 배치 계산 → Renderer)을 축소해 쓴다.
- 이유: 대부분은 어제 하던 프로젝트를 이어서 하려고 앱을 켠다. 다른 Git 앱의 "최근 저장소 목록"보다 버튼 하나로 이어서 하는 편이 빠르고, 상태를 문장으로 말하면 Git을 몰라도 어디서 멈췄는지 안다. 색을 큰 노선도 한 곳에 모으면 먹색 모노 틀(D-026)에서 눈이 갈 곳이 하나가 된다. 다크 테마의 그래프 색은 글자 대비 4.5:1에 못 미치는 것이 있어(`--graph-2`는 다크 `--bg`에서 약 3.5) 글자에는 쓰지 않는다.
- 대안: 최근 저장소 목록만(흔한 Git 앱 방식, 이어서 할 곳이 눈에 띄지 않음), 처음 실행 마법사 화면(한 번만 쓰는 화면이 따로 생기고 설정을 미루기 어려움), 노선도 없이 글자만(hiGit의 특징인 노선도와 이어지지 않음).
- 영향: `docs/spec.md` 화면 구성의 "시작 화면" 행. `docs/design.md`에 글자 크기 26px(새 토큰 `--font-size-display`)과 시작 화면 색 규칙을 넣는다. 노선도 부분은 D-017이 확정되어야 구현한다(그 전에는 노선도 자리를 비워 둔다). 처음 실행의 이름·이메일 설정은 1b 뒤 별도 계획에서 다룬다. 최근 프로젝트별 상태는 core Query(`query_project_summary`)로 가져오고 화면이 git을 부르지 않는다. 계획: `docs/plans/003-start-screen.md`.

## D-032 앱을 켜면 마지막 프로젝트를 바로 열고, 최근 프로젝트 목록은 앱 데이터 폴더에 둔다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 앱을 켜면 최근 프로젝트 목록의 맨 앞 프로젝트를 바로 작업 공간으로 연다. 목록이 비었거나, 그 폴더가 사라졌거나, 그 폴더가 더 이상 Git 저장소의 최상위가 아니면 시작 화면을 보여주고 맨 위에 한 줄로 까닭을 알린다. 이때 다른 프로젝트를 대신 열지 않는다. 시작 화면은 작업 공간 상단 바의 프로젝트 메뉴 "다른 프로젝트 열기"로 온다. 최근 프로젝트 목록은 사용자 앱 데이터 폴더의 `recent.json`(형식 버전, 경로, 이름, 마지막으로 연 시각, 최대 20개)에 둔다. 폴더 위치는 `crates/platform`이 정한다: Windows `%LOCALAPPDATA%\dev.higit.desktop\`, Ubuntu `$XDG_DATA_HOME/dev.higit.desktop/`(없으면 `~/.local/share/dev.higit.desktop/`). 목록 읽기·쓰기는 `crates/core`의 한 모듈이 하고, 폴더를 열어 저장소로 확인될 때(폴더 열기, 버전 관리 시작, 최근 프로젝트 열기) core가 목록을 갱신한다.
- 이유: 시작 화면은 이어서 할 곳을 고르는 화면인데, 대부분은 마지막 프로젝트를 고른다. 한 번 더 누르지 않게 바로 연다. 경로는 컴퓨터마다 다르므로 로밍되는 폴더가 아니라 로컬 앱 데이터에 둔다. 위치를 Tauri가 쓰는 `app_local_data_dir`과 같게 하면 웹뷰 데이터와 한 폴더에 모인다. 다른 프로젝트를 몰래 열면 사용자가 엉뚱한 프로젝트에서 작업할 수 있어 시작 화면에서 고르게 한다.
- 대안: 앱을 켤 때마다 시작 화면(한 번 더 눌러야 함), 목록을 Tauri store 플러그인으로(의존성이 늘고 core가 Tauri를 알게 됨), 앱 crate에서 Tauri 경로 API로 위치를 정함(OS별 경로 규칙이 platform 밖에 생김), 로밍 `%APPDATA%`(다른 컴퓨터에 없는 경로가 따라감).
- 영향: `platform`에 앱 데이터 폴더와 경로 비교(Windows는 대소문자 무시) 함수를 둔다. core는 앱 identifier(`dev.higit.desktop`, D-009)를 상수로 갖고, 테스트로 `tauri.conf.json`과 같은지 확인한다. Tauri 명령 `recent_list`, `project_open`(기존 `repo_open` 대체), `recent_remove`가 생긴다. 앱을 켤 때 열기, 최근 목록, 폴더 고르기, 프로젝트 메뉴의 열기는 모두 core `Core::open_project` 한 함수와 화면 `useOpenProject` 한 훅을 거친다. 저장소 신뢰 확인은 나중에 그 한 곳에 넣는다. 이 목록은 Git 상태가 아니므로 Action·Query가 아니다(D-010). 폴더 우클릭·명령줄로 열 때(반복 5)는 시작 화면을 건너뛰고 그 폴더를 연다. 단일 인스턴스(반복 5) 전에는 앱 두 개가 동시에 쓰면 나중 쓰기가 이긴다.

## D-033 시작 화면의 폴더 열기·복제는 굵은 글자와 단축키로, 단축키는 한 표에서 관리한다
- 상태: 확정
- 날짜: 2026-10-15
- 결정: 시작 화면 상단 바 오른쪽에 "폴더 열기 Ctrl+O", "복제 Ctrl+Shift+O"를 테두리 없는 굵은 글자(600) 버튼과 옅은 단축키 글자로 둔다. "복제"는 `<Term id="clone" />`이다. 앱의 단축키는 프론트의 단축키 표(`src/lib/shortcuts.ts`) 한 곳에 모으고, 표 안에서 겹치지 않는지 테스트한다. 단축키는 `KeyboardEvent.code`(예: `KeyO`)로 판정하고 한글 조합 중(`isComposing`)이면 무시한다. 복제와 Ctrl+Shift+O는 복제 기능이 생기는 반복 4에 함께 넣고, 그 전에는 보이지 않게 한다.
- 이유: 시작 화면의 주 버튼은 "이어서 하기" 하나여야 한다(design.md). 폴더 열기·복제까지 버튼이면 주 버튼과 다툰다. Ctrl+O는 운영체제와 브라우저에서 "열기"로 익숙하고, Ctrl+Shift+O는 GitHub Desktop(Windows)의 "저장소 복제"와 같다. Windows·GNOME 시스템 단축키, WebView2가 문서로 밝힌 브라우저 단축키(찾기·인쇄·새로 고침·확대·개발자 도구), 앱의 기존·계획 단축키(Ctrl+Enter 버전 저장, Ctrl+K 명령 팔레트)와 겹치지 않는다. 한글 입력 상태에서는 `key`가 `ㅐ`처럼 바뀌므로 `code`로 판정해야 한다.
- 대안: 테두리 버튼 두 개(주 버튼과 다툼), 복제를 비활성으로 미리 보여주기(누를 수 없는 것이 처음 화면에 생김), 복제 단축키 Ctrl+Shift+N(크롬 시크릿 창과 같아 익숙한 뜻과 어긋남), Ctrl+Shift+C(WebView2 개발자 도구 요소 검사와 겹침).
- 영향: 단축키가 있는 Action은 나중에 `ActionMeta`의 단축키도 이 표와 겹치지 않는지 같은 테스트로 확인한다. 브라우저의 Ctrl+Shift+O(북마크 관리자)는 웹뷰에 없지만, WebView2·WebKitGTK에서 실제로 앱에 전달되는지 두 OS에서 손으로 확인한다. "설정" 글자는 설정 화면이 생길 때 같은 자리에 넣는다.
