## 결론
- 배치: 기본은 **2단 + 상단 바**. 브랜치 목록은 상단 바 드롭다운에서 열고, 설정 "브랜치 목록 항상 보기"를 켜면 왼쪽 사이드바가 생겨 3단이 된다.
- 색: **먹색 모노**. 틀은 거의 무채색, 주 버튼은 흑연색 `#4A5059` 채움(처음 안 `#24292F`은 너무 진하다는 의견으로 한 단계 밝힘). 파랑은 선택·포커스·링크에만. 색은 브랜치 선과 파일 상태(추가·수정·삭제), 위험 작업에만 쓴다.
- "AI 느낌" 피하기: 아래 표의 패턴을 쓰지 않는다.
- 용어: `docs/research/terminology.md`의 기준을 따른다. 억지 번역 대신 이미 익숙한 말, 굳은 외래어는 그대로.

## "AI가 만든 것 같은" 화면의 원인
AI는 지시가 모호하면 학습 데이터에서 가장 흔한 선택으로 채워 튜토리얼의 평균 같은 화면을 만든다. 보라색이 많은 이유는 Tailwind 예제 기본색(indigo-500)이 널리 복사됐기 때문이라는 분석이 있다.

| 흔한 패턴 | hiGit에서는 |
| --- | --- |
| 보라·남색 강조색과 그라데이션 | 무채색 틀 + 먹색 주 버튼. 파랑은 선택·포커스·링크에만 |
| 모든 상자에 같은 둥근 모서리와 그림자 | 구분은 1px 선. 그림자는 떠 있는 것(메뉴, 대화상자, 툴팁)에만 |
| 가운데 정렬, 큰 제목, 아이콘 3개 나열 | 왼쪽 정렬 목록. 빈 화면도 한 줄 설명 + 버튼 하나 |
| 여러 색을 고르게 나눠 쓴 팔레트 | 색은 의미가 있을 때만: 브랜치 선, 추가·수정·삭제, 위험 작업 |
| Inter·Roboto 같은 기본 글꼴 | Pretendard + JetBrains Mono |
| 흔한 페이드·호버 효과 | 움직임은 150ms 안팎, 상태가 바뀔 때만 |
| 카드 왼쪽 색 띠, 선택지마다 둥근 카드를 띄워 쌓기 | 한 상자 안을 1px 선으로 나누고 색은 점과 코드 바탕에만 |
| "**항목:** 설명" 꼴의 굵은 머리말 목록 반복 | 평범한 문장 두세 개, 비교가 필요하면 표 |
| "그만두기 (원래대로)" 같은 괄호 보충 | 버튼은 동사 하나, 보충은 툴팁이나 둘째 줄 |

## 참고한 앱과 가이드
앱 관찰은 사용 경험 기반 정리, 가이드는 원문 확인.

| 참고 | 빌려올 점 | 피할 점 |
| --- | --- | --- |
| GitHub Desktop | 상단 바 "저장소 · 브랜치 · 받기/올리기", 왼쪽 "변경 사항/기록" 탭. 비전공자가 가장 빨리 익히는 구조 | 기록 화면에서 브랜치 구조가 거의 안 보임 |
| Sublime Merge | 글자 위계만으로 정리된 촘촘한 화면 | 정보가 많아 초보에게 어려움 |
| Fork · Tower | 왼쪽 사이드바(브랜치·태그), 깔끔한 그래프 | 3단 고정이라 좁은 창에서 답답함 |
| Things 3 · Linear | 무채색 바탕에 색 하나, 넉넉한 줄 간격, 키보드 중심 | 지나친 여백은 Git 목록 밀도를 떨어뜨림 |

| Fluent 2 색 (https://fluent2.microsoft.design/color) | 무채색이 바탕, 브랜드 색은 버튼·선택에만, 넓은 면 금지. 의미 색은 장식 금지 | Windows 느낌이 너무 강하면 Ubuntu에서 어색함 |

## 배치 세 가지
같은 상황(로그인 기능 브랜치에서 파일 3개를 고친 상태) 기준.

### A. 2단 + 상단 바 (추천)
```
┌ [프로젝트 my-shop] [● 브랜치 로그인 기능 ▾]        새로 고침 [올리기 ↑2] ┐
├───────────────────────────┬──────────────────────────────────────────────────┤
│ 변경 사항 3 | 버전 기록    │ src/login/화면.tsx                        +12 −3 │
│ 수 src/login/화면.tsx  ◀   │   export function LoginScreen() {               │
│ 추 src/login/비밀번호.ts   │ -   return <Form />                             │
│ 삭 src/old-auth.ts         │ +   const [pw, setPw] = useState("")            │
│ [무엇을 바꿨나요?       ]  │   }                                             │
│ [■■■■ 버전 저장 ■■■■]     │                                                  │
└───────────────────────────┴──────────────────────────────────────────────────┘
```
- 좋은 점: 볼 곳이 두 군데라 길을 잃지 않음. 좁은 창에 강함. GitHub Desktop과 비슷해 낯설지 않음.
- 보완: 브랜치 목록은 상단 바 드롭다운. 설정으로 왼쪽 사이드바를 켜면 B가 됨.

### B. 3단 (사이드바 + 목록 + 비교)
- 좋은 점: 브랜치가 늘 보여 브랜치를 자주 오가는 사람에게 빠름. Fork·Tower 사용자에게 익숙.
- 아쉬운 점: 초보에게 볼 곳이 셋이라 부담. 노트북에서 비교 칸이 좁아짐.

### C. 할 일 흐름 중심
- 상단에 "1 고치기 → 2 버전 저장 → 3 올리기" 단계, 가운데 카드 하나에 지금 할 일.
- 좋은 점: "지금 뭘 해야 하지?"에 바로 답함.
- 아쉬운 점: 익숙해지면 느리고 다른 Git 앱과 달라 낯섦. A 안의 "처음 쓰는 사람 안내 모드"로 나중에 넣는 게 적당.

## 세부 규칙
| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| 밀도 | 목록 행 32px, 글자 13px, 간격 4px 단위 | Git 목록은 한 화면에 많이 보여야 함 |
| 구분 | 패널 사이 1px 선, 바탕 단계는 3단(bg · surface · sunken)까지만 | 그림자·카드 대신 선이 차분함 |
| 모서리 | 버튼·입력 6px, 창 안 패널 0, 떠 있는 것만 8px | 모두 둥글면 템플릿처럼 보임 |
| 상단 바 | 왼쪽: 프로젝트·브랜치 / 오른쪽: 새로 고침·동기화. 컨트롤 5개 이하 | GNOME HIG "적게, 맥락에 맞게" |
| 주 버튼 | 화면당 하나, 흑연색 `#4A5059` 채움. 위험 작업은 빨간 글자 테두리 버튼 | 누를 곳이 한눈에 |
| 강조색 파랑 | 선택 막대, 키보드 포커스, 링크에만 | Fluent 2: 브랜드 색을 넓은 면에 쓰지 않기 |
| 상태 표시 | 색 + 글자(추·수·삭) 함께 | 색만으로 구분하면 색약 사용자가 못 봄 |
| 빈 화면 | 그림 없이 한 줄 설명 + 버튼 하나, 왼쪽 정렬 | 가운데 큰 일러스트는 템플릿 느낌의 대표 원인 |

| 문구 | 괄호로 덧붙이는 설명 금지. 버튼은 동사 하나, 보충은 Term 툴팁이나 둘째 줄로. 예: "합치기 그만두기 (원래대로)" → "합치기 그만두기" | 괄호 보충은 자동 생성 문구의 대표 습관 |

## 비교 보기 (diff)
처음 쓰는 사람이 헷갈리는 이유: 코드가 두 벌인데 어느 쪽이 예전이고 지금인지 아무도 말해 주지 않음.

- 맨 위 한 문장: "마지막 저장(10월 14일)과 지금 파일을 비교해요 · 2줄 추가, 1줄 삭제". 버전 기록에서 열면 "이 버전 직전과 비교해요".
- 기본은 "한 줄로 보기"(unified). "나란히 보기"는 선택, 고른 값을 기억.
- 나란히 보기에서는 양쪽 머리에 이름표: "예전: 마지막 저장 · 날짜 · 메시지" / "지금: 내 파일 · 아직 저장 안 함". a/b, ours/theirs 금지.
- 바뀐 단어만 진한 배경(단어 단위 하이라이트).
- 안 바뀐 부분은 "변경 없는 12줄 · 펼치기"로 접기.
- 색 + 기호(+/−) 항상 함께.

## 충돌 해결 (conflict)
어려운 이유: ① 왼쪽·오른쪽 중 어느 쪽이 내 것인지 모름 ② `<<<<<<<` 표시가 파일에 섞임 ③ 무엇을 눌러야 끝나는지 모름.
화면은 질문 하나를 던진다: "두 브랜치가 같은 줄을 다르게 고쳤어요. 어느 쪽을 남길까요?"

```
┌ 합치는 중: ● main을 ● 로그인 기능에 합치고 있어요 · 충돌 3곳 중 2곳 남음   [합치기 그만두기] ┐            
├ 겹친 파일          ┬ src/login/화면.tsx · 14번째 줄                                              ┤
│ ✓ src/config.ts    │ ┌ ● 내 브랜치: 로그인 기능 · 준호 · 10월 7일 · "비밀번호 확인 추가"   [✓ 이걸로] ┐ │
│ ● 화면.tsx · 2곳   │ │   return <Form title="로그인하기" onSubmit={check} />                      │ │
│ 문제없이 합쳐진 5개 │ └──────────────────────────────────────────────────────────────────────┘ │
│                    │ ┌ ● 합칠 브랜치: main · 민지 · 10월 8일 · "버튼 문구 통일"        [이걸로] ┐ │
│                    │ │   return <Form title="로그인" submitLabel="들어가기" />                    │ │
│                    │ └──────────────────────────────────────────────────────────────────────┘ │
│                    │ [둘 다 쓰기] [직접 고치기]  고치기 전 원래 코드 보기 ▾                      │
│                    │ ┌ 저장될 모습: 이 곳은 이렇게 저장돼요 ┐                                  │
│                    │ │ ...                                    │        ← 이전 곳  [다음 충돌 →] │
└────────────────────┴──────────────────────────────────────────────────────────────────────────┘
```

| 원칙 | 화면에서 | 흔한 Git 도구는 |
| --- | --- | --- |
| 위아래로, 이름표 달기 | 카드 머리에 "내 브랜치 · 사람 · 날짜 · 저장 메시지". 브랜치 색 점은 노선도와 같은 색 | 왼쪽 ours, 오른쪽 theirs |
| 한 번에 한 곳 | "3곳 중 2곳 남음", 다음·이전. 파일 목록에 ✓/● | 표시가 파일 전체에 흩어짐 |
| 결과를 먼저 보여주기 | 고르면 "저장될 모습"가 즉시 바뀜 | 고른 뒤 파일을 다시 열어 봐야 앎 |
| 표시 문자 숨기기 | `<<<<<<<`, `=======` 절대 노출 안 함. "직접 고치기"도 깨끗한 편집 칸 | 표시 문자가 섞인 원본 |
| 언제든 빠져나가기 | "합치기 그만두기" 늘 보임. 누르면 `git merge --abort` | 명령을 알아야 취소 |
| 원래 코드는 필요할 때만 | "고치기 전 원래 코드 보기"로 접음. 툴팁에 base | 세 칸이 한꺼번에 |
| 끝이 분명하게 | 모든 곳을 고르면 주 버튼이 "합치기 마치기"로 바뀜 | add, commit을 직접 해야 끝남 |

색 규칙: 이 화면에서 색은 브랜치를 뜻할 때만 쓴다. 내 브랜치는 어디서나 초록 `--l2`, 합칠 브랜치는 어디서나 파랑 `--l1`. 카드 왼쪽 띠, 코드 바탕, 저장될 모습의 줄 바탕이 고른 브랜치의 색을 따른다. 고른 카드는 "✓ 이걸로" 버튼이 흑연색으로 채워지고 안 고른 카드는 흐려진다. 진행 표시 ✓·●와 선택 막대는 먹색. 강조색 파랑은 main 브랜치 색과 겹치므로 이 화면에서는 쓰지 않는다.

용어: "내 브랜치"(ours), "합칠 브랜치"(theirs). 호버하면 원래 이름. 리베이스에서는 Git의 ours/theirs 뜻이 뒤바뀌지만 hiGit은 항상 "내 브랜치 / 합칠 브랜치"로 같은 뜻을 유지한다(구현 시 rebase일 때 매핑을 뒤집어야 함).

### 충돌 화면 2안: 제안부터 보여주기
실제 충돌은 같은 줄의 다른 부분을 고친 경우가 많다. 그런 곳은 둘 다 살린 제안을 먼저 보여주고, 같은 글자를 다르게 고친 곳만 1안의 카드 두 장으로 묻는다.

```
┌ 합치는 중 ● main을 ● 로그인 기능에 합치고 있어요     [하나씩 보기|문서처럼 보기] [합치기 그만두기] ┐
├ 충돌 3군데              ┬ 로그인 버튼 문구                                                    ┤
│ ✓ 설정 기본값              │ 두 브랜치가 같은 줄의 서로 다른 부분을 고쳤어요. 둘 다 살린 안을 만들었어요. │
│   config.ts · main 쪽으로   │ ┌ 제안   초록 로그인 기능 · 준호  파랑 main · 민지   Space 누르는 동안 예전 ┐ │
│ ● 로그인 버튼 문구         │ │ return <Form title="로그인하기" onSubmit={check} submitLabel="들어가기" /> │ │
│   화면.tsx 14줄 · 제안 있음 │ │              ~~~~~~~~ 초록      ~~~~~~~~~~ 초록  ~~~~~~~~~~~~~~ 파랑  │ │
│ ○ 비밀번호 길이            │ └────────────────────────────────────────────────────────────────┘ │
│   화면.tsx 22줄 · 골라야 함 │ [이대로 합치기] [한쪽만 고르기] [직접 고치기]                          │
│                            │ 쓰고 나서도 복구 화면에서 합치기 전으로 되돌릴 수 있어요.                 │
└────────────────────────────┴────────────────────────────────────────────────────────────────────┘
```

- 왼쪽 목록은 충돌 단위. 이름은 바뀐 줄 근처의 함수 이름이나 첫 단어로 만든다.
- 상태 셋: ✓ 정함, ● 제안 있음, ○ 골라야 함.
- 누가 고친 글자인지 브랜치 색 밑줄. 노선도와 같은 색.
- 제안은 확실할 때만. 양쪽이 같은 글자를 다르게 고쳤으면 제안하지 않는다. 추측으로 코드를 만들지 않는다.
- 구현 메모: 겹친 덩어리를 base 기준으로 단어 단위 3-way 비교해서, 양쪽 수정 범위가 겹치지 않으면 제안을 만든다. 겹치면 "골라야 함".

### 문서처럼 보기
워드처럼 파일 한 벌 안에서 고친 곳을 차례로 받거나 뺀다. 글이나 설정 파일이 많은 사람에게 익숙하다. 같은 글자를 다르게 고친 곳은 "초록 쪽 / 파랑 쪽" 둘 중 하나를 고르게 한다.

### 비교 화면에 더할 것
- Space를 누르고 있는 동안 예전 모습으로 바꾸는 깜빡이 비교. 한 줄로 보기와 나란히 보기 모두에서.
- 그림 파일은 끌어서 보는 전후 막대. 크기가 다르면 "가로 120 → 160" 한 줄.
- 긴 파일은 맨 위에 바뀐 곳 목록. 누르면 그 자리로.
